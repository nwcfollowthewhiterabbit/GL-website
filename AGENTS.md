# Правила работы с репозиторием

Этот репозиторий — единый источник правды проекта `Green Leaf Pacific Website`. Правила
обязательны для разработчиков и автономных инженерных агентов.

## Параметры проекта

- цель продукта: `Provide an ERPNext-backed B2B storefront, customer account, and compliant Windcave hosted payment flow for Green Leaf Pacific`;
- текущий этап: `Testing and payment UAT readiness`;
- исходный репозиторий и ветка: `nwcfollowthewhiterabbit/GL-website`, `main`;
- runtime: `Docker Compose storefront and Node integration API connected to ERPNext`;
- язык пользовательского интерфейса: `en`;
- язык внутренней документации: `ru`;
- префикс тестовых данных: `GL-WEB-E2E`;
- владелец приёмки: `Green Leaf Pacific project team`.

Все токены должны быть заменены при инициализации проекта. Неизвестное
помечается `TODO(project)` и переносится в открытые вопросы; его нельзя выдавать
за согласованный факт.

## Обязательный первый проход

Перед изменением:

1. подтвердите текущую цель, проверьте `git status` и чужие изменения;
2. прочитайте `README.md`, текущий scope и документы затронутого процесса,
   домена, прав, качества и эксплуатации;
3. изучите существующую реализацию и проверки;
4. при разрешённом доступе подтвердите runtime, данные, права и логи;
5. для изменения поведения зафиксируйте baseline сквозного сценария, а для
   документационной задачи проверьте факты, ссылки и согласованность.

Наличие страницы, кнопки или функции не доказывает готовность процесса. Не
удаляйте рабочее решение и не меняйте существующие данные без доказанной
необходимости и безопасного пути перехода.

## Definition of Ready

До реализации функции должны быть определены:

1. акторы, цели и права;
2. предусловия и входные данные;
3. основной сценарий и исключения;
4. состояния, переходы и системные эффекты;
5. бизнес-инварианты;
6. защита от повторов и дублей;
7. отмена или контролируемое исправление;
8. отчёты, аудит и критерий завершения;
9. проверяемые критерии приёмки;
10. неблокирующие открытые вопросы.

Сквозной сценарий описывается так:

```text
предусловие → действие → состояние → системный эффект → контроль → исправление
```

Неизвестное, способное существенно изменить реализацию, блокирует разработку до
решения владельца требования.

## Принципы реализации процессов

- Предпочитайте штатные механизмы выбранной платформы. Обходной интерфейс
  требует доказанной необходимости и ADR.
- Критические ограничения обеспечиваются backend и данными. UI предотвращает
  очевидную ошибку и объясняет путь, но не заменяет защиту.
- Действие создания следующего объекта доступно только после допустимого
  состояния предыдущего шага, проверяет права и принадлежность данных, создаёт
  обратимое предварительное состояние и заполняет только однозначно выводимые
  данные.
- Повтор операции по бизнес- или идемпотентному ключу открывает существующий
  результат. Частичные операции проверяют неисполненный остаток и получают
  отдельный ключ.
- У каждой роли одна понятная точка входа. Видимость навигации не является
  защитой: отдельно проверяются прямой URL, API, отчёты и изоляция данных.

## Классификация обратной связи

- **Blocker** — основной процесс текущего этапа нельзя завершить;
- **Bug** — поведение нарушает согласованную логику;
- **Data/configuration issue** — причина в данных, правах или настройке;
- **UX improvement** — процесс корректен, но неудобен;
- **New requirement** — новая бизнес-логика;
- **Out of scope** — относится к следующему этапу.

Сначала устраняются подтверждённые блокеры текущего этапа. Принятое требование
переносится в требования, нерешённое — в открытые вопросы, отложенное — в
backlog.

## Документация и инструкция пользователя

Функциональное изменение обновляет применимые требования, процесс, доменную
модель, матрицу доступа, roadmap/backlog, тесты, `CHANGELOG.md` и инструкцию.
Пользовательская функция без интерфейса и инструкции на
`en`, а также сценария проверки не готова к передаче.

Инструкция описывает только фактическое поведение развёрнутой версии. Пути и
ссылки проверяются под указанной ролью. Изменяйте только затронутые шаги,
разделяя основной поток, исправление ошибки и контрольный тест.

## Инженерный цикл изменения

1. Подтвердить цель, scope и baseline.
2. Сформулировать инвариант и ожидаемый результат.
3. Реализовать минимальное системное изменение.
4. Добавить применимые backend-защиту, UI-ограничение и идемпотентность.
5. Обновить проверки и затронутую документацию.
6. Выполнить обязательные repository/unit/readiness-команды, создать и отправить
   source/release commit **до изменения runtime**. Артефакт строится только из
   этого commit.
7. После push подтвердить точное равенство SHA локального `HEAD` и удалённой
   ветки, а также успешный CI run именно для этого SHA.
8. До мутации определить точный target и его состояние. Для доказанно пустой
   цели первого deploy backup отмечается `N/A` только со ссылкой на evidence
   пустоты. Любое существующее состояние блокирует first-deploy и требует
   сценария update с проверенным backup.
9. Выполнить штатные deploy, migrate/setup и операции с cache/assets, если они
   применимы к стеку.
10. Проверить точный runtime, внешний endpoint, данные, роли, прямой URL/API,
    основной, ошибочный и повторный пути.
11. Удалить временные данные с уникальным
    `GL-WEB-E2E-<RUN_ID>`.
12. Зафиксировать evidence отдельным документационным commit, если оно
    изменилось; выполнить push и повторно подтвердить чистое дерево, удалённый
    SHA и CI.

## Runtime, backup и миграции

Изменение внутри работающего runtime временно. Ручное исследование до завершения
переносится в код, конфигурацию, fixture, patch, миграцию или идемпотентный
setup.

Целевой цикл:

```text
чистый Git commit → подтверждённый удалённый SHA и CI →
evidence пустой цели для first deploy ИЛИ проверенный backup для update →
уникальный артефакт из commit → изменение runtime без потери данных →
migrate → идемпотентный setup → тесты → smoke-тест
```

Backup включает данные, конфигурацию и пользовательские файлы, хранится вне
заменяемого runtime и проверяется до мутации. Единственное допустимое исключение
— первый deploy на цель, пустота которой доказана read-only проверками и
зафиксирована в evidence; для неё backup имеет статус
`N/A — target proven empty`. Если обнаружены экземпляр, данные, конфигурация,
файлы или иное состояние, first-deploy обязан завершиться отказом: применяется
update с проверенным backup. Первый deploy, обновление, restore и rollback —
разные воспроизводимые сценарии. Deploy обязан завершиться ошибкой при сбое
обязательной проверки пустоты либо backup, migrate, setup или validation.

Без отдельного разрешения запрещены удаление постоянных данных, необратимая
миграция без проверенного backup, перезапись используемого release-артефакта и
хранение секретов в Git.

## Минимальные уровни проверки

1. **Repository:** структура, ссылки, секреты, конфигурация, syntax/lint.
2. **Instance:** миграции, setup, роли, права, обязательные записи, маршруты и
   настройки.
3. **Domain integration:** инварианты, состояния, изоляция, повторы и ошибки.
4. **Golden-path E2E:** процесс от входа до проверяемого результата.
5. **UI E2E:** реальный браузер, роли, формы, действия, повтор и ссылки.
6. **Cleanup:** уникальные тестовые записи удалены после проверки.

Набор применяется пропорционально изменению. Документационная задача не требует
deploy; изменение пользовательского процесса требует проверки развёрнутого
экземпляра и ролей.

## Обязательные команды проверки

Из корня репозитория перед commit и повторно перед передачей результата
выполняются:

```bash
python3 scripts/check_repository.py
python3 -m unittest discover -s tests -p "test_*.py"
python3 scripts/check_release_readiness.py
```

Первые две команды всегда должны завершаться с кодом `0`. Для состояния
`automation.state = "scaffold"` третья команда обязана завершиться ненулевым
кодом и перечислить незакрытые gates; её успех в scaffold является ошибкой
контракта. Для `automation.state = "configured"` третья команда обязана
завершиться с кодом `0`.

После каждого push выполните:

```bash
git status --short
test -z "$(git status --porcelain)"
current_branch="$(git branch --show-current)"
test -n "$current_branch"
test "$current_branch" = "main"
local_sha="$(git rev-parse HEAD)"
remote_sha="$(git ls-remote --exit-code origin \
  "refs/heads/$current_branch" | awk 'NR == 1 { print $1 }')"
test -n "$remote_sha"
test "$local_sha" = "$remote_sha"
```

Рабочее дерево должно быть чистым, `current_branch` должна точно совпадать с
настроенной веткой `main`, а локальный и удалённый SHA — быть
равными. Затем через настроенный read-only API/CLI провайдера CI подтвердите
успешный run для `local_sha` и сохраните ссылку или run ID в release evidence.
Точная команда CI фиксируется в `docs/08-operations/operational-names.md`; пока
она не настроена или run относится к другому SHA, изменение не готово к
передаче.

## Definition of Done

Применимые пункты подтверждены: реализация и документация находятся в Git;
backend защищает инварианты; права и UI/API проверены; повтор не создаёт дубль;
локализация добавлена; setup/migrate воспроизводимы; для update проверен backup,
а для first-deploy зафиксировано evidence пустой цели и backup отмечен `N/A`;
уникальный артефакт собран из отправленного commit; smoke-тест пройден; тестовые
данные очищены; инструкция, changelog и журнал релиза актуальны; ограничения
названы; обязательные команды дали ожидаемый результат для текущего состояния;
commit отправлен, рабочее дерево чистое, локальный и удалённый SHA совпадают,
CI успешен именно для этого SHA.

## Безопасность, Git и коммуникация

- Не выводите секреты в логи, документы, commits и сообщения. В Git допустим
  только пример конфигурации без секретных значений.
- Перед опасной операцией точно определите target, хранилище и backup.
- Не перезаписывайте пользовательские или чужие незавершённые изменения.
- Коммиты должны быть небольшими и содержательными.
- Сообщайте установленные факты, проверки и остаточный риск.
- Для заказчика используйте формат: причина → исправление → что проверить.
- Исходящие статусы и протоколы ведите по
  `docs/09-communications/README.md`; сообщение не заменяет требование или ADR.
- Не обещайте отсутствие всех будущих ошибок; называйте закрытый класс риска.
